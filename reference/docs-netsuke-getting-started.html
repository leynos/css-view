Netsuke

A modern, declarative build system designed to be intuitive, fast, and safe. Define what you want to build, not how.

What is Netsuke?

Netsuke is not just a make replacement, but a build system compiler. You describe your build process in a human-readable YAML manifest (Netsukefile), leveraging Jinja templating for dynamic logic. Netsuke compiles this into an optimized build plan executed by the high-performance Ninja build system.

Core Philosophy

  • Declarative: Define what you want to build, not how step-by-step
  • Dynamic where needed: Use Jinja for variables, loops, conditionals, file globbing
  • Static Execution Plan: All dynamic logic resolved before execution
  • Safety First: Automatic shell escaping prevents command injection
  • Fast Execution: Leverages Ninja for efficient dependency tracking

Key Benefits

  • Human-readable YAML configuration
  • Jinja templating for dynamic builds
  • Ninja-powered parallel execution
  • Automatic dependency resolution
  • Built-in safety features

Getting Started

Build from source and start building in minutes. Install. Configure. Verify.

1

Install

Build Netsuke from source using Cargo. Ensure ninja is available in your PATH.

Terminal 
cargo build --release
# The executable will be in target/release/netsuke
2

Configure

Create a Netsukefile in your project root.

Netsukefile 
netsuke_version: "1.0.0"

vars:
  cc: gcc
  src_dir: src

targets:
  - name: build/main.o
    command: "{{ cc }} -c {{ src_dir }}/main.c -o build/main.o"
    sources: src/main.c

defaults:
  - build/main.o
3

Verify

Run Netsuke to build your targets.

Terminal Output 
netsuke

[1/1] Compiling build/main.o
Build completed successfully!

The Netsukefile Manifest

The YAML file describing your entire build process with clear, structured sections.

Top-Level Structure

Complete Netsukefile Example 
# Mandatory: Specifies the manifest format version
netsuke_version: "1.0.0"

# Optional: Global variables accessible throughout
vars:
  cc: gcc
  src_dir: src

# Optional: Reusable Jinja macros
macros:
  - signature: "compile_cmd(input, output)"
    body: |
      {{ cc }} -c {{ input }} -o {{ output }}

# Optional: Reusable command templates
rules:
  - name: link
    command: "{{ cc }} {{ ins }} -o {{ outs }}"

# Optional: Phony targets for setup or meta-tasks
actions:
  - name: clean
    command: "rm -rf build *.o"

# Required: Defines the build targets
targets:
  - name: build/main.o
    command: "{{ compile_cmd('src/main.c', 'build/main.o') }}"
    sources: src/main.c

  - name: my_app
    rule: link
    sources: build/main.o

# Optional: Default targets to build
defaults:
  - my_app

Defining Rules

Rules encapsulate reusable build commands and scripts for consistent execution.

Rule Definition Example 
rules:
  - name: compile
    command: "{{ cc }} {{ cflags }} -c {{ ins }} -o {{ outs }}"
    description: "Compiling {{ outs }}"
    deps: gcc

Rule Components

name

Unique string identifier for the rule

command/script/rule

The action to perform (mutually exclusive)

description

User-friendly message during build

deps

Dependency file format (gcc or msvc)

Defining Targets and Actions

Targets define what to build or what action to perform with flexible configuration options.

Target Examples 
targets:
  # Building an object file using a rule
  - name: build/utils.o
    rule: compile
    sources: src/utils.c
    deps:
      - build/utils.h
    vars:
      cflags: "-O0 -g"

  # Linking executable with inline command
  - name: my_app
    command: "{{ cc }} build/main.o build/utils.o -o my_app"
    sources:
      - build/main.o
      - build/utils.o
    order_only_deps:
      - build_directory

  # Phony action
  - name: package
    phony: true
    command: "tar czf package.tar.gz my_app"
    deps: my_app

  # Always-run target
  - name: timestamp
    always: true
    command: "date > build/timestamp.txt"

Jinja Templating in Netsuke

Netsuke uses MiniJinja to add dynamic capabilities with safe, structured templating.

Basic Syntax

Variables:

{{ my_variable }}

Expressions:

{{ 1 + 1 }}, {{ sources | map('basename') }}

Control Structures:

{% if enable %}...{% endif %}

Processing Order

  1. 1. Initial YAML Parse: Load raw file structure
  2. 2. Template Expansion: Evaluate foreach, when
  3. 3. Deserialization: Convert to typed Rust structs
  4. 4. Final Rendering: Render Jinja in string fields

Dynamic Target Generation

foreach and when Examples 
targets:
  # Generate a target for each .c file in src/
  - foreach: glob('src/*.c')
    name: "build/{{ item | basename | replace('.c', '.o') }}"
    command: "{{ cc }} -c {{ item }} -o {{ outs }}"
    sources: "{{ item }}"
    when: "{{ item | basename != 'exclude.c' }}"

Testing & CI Templates

Drop these templates into your CI pipeline for immediate integration.

GitHub Actions

Create .github/workflows/ci.yml.

ci.yml 
name: CI
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v3
    - name: Install Ninja
      run: sudo apt-get install ninja-build
    - name: Build Netsuke
      run: cargo build --release
    - name: Run Build
      run: ./target/release/netsuke
